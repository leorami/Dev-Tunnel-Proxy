# RC2 v86 — restore constrained HTTP-only route audit without regressing security

**Source-only CTO parallel lane. NOT deployed. Not a replacement for AI healing or browser UAT.**

## Directly observed failure and why the legacy endpoint cannot be unblocked

The production security policy blocks `POST /devproxy/api/ai/audit` alongside the old self-healing paths. In the underlying `utils/calliopeHealing.js`, `runSiteAuditor()` invokes local `npm ci`, `npx -y tsc`, shell-built Node commands and a Docker fallback, may fetch arbitrary supplied `url`, and creates audit report files. Bypassing the current guard would reintroduce code execution, network access, write paths, and nontransactional escalation in the nonroot API. We must not restore functionality by flipping a deny flag.

## CTO implementation

- `utils/rc2-secure-http-audit.cjs` supplies an authenticated read-only HTTP **HEAD** probe of the existing `dev-proxy:80` service. The network destination, method, port, and headers are literals. The owner-supplied URL is only a strict route selector: either an absolute owner-trusted configured Origin or `http://dev-proxy`, or a conservative relative route. It is never contacted and never controls destination host/port, headers, cookies, methods, request body, or redirection. It is forbidden to provide userinfo, ports, query strings, fragments, encoded bytes, dot segments, duplicate slashes, administration prefixes or arbitrary protocol/hostname. First-party controls enforce 2KiB JSON body limit and a bounded network timeout; response emits no private source paths, usernames, headers, token, URL or redirect Location. It never follows redirect or fetches a response body.
- `utils/proxyConfigAPI.js` integrates the exact `POST ai/audit` request **only in secure/spool mode**, AFTER existing authentication and trusted-Origin CSRF verification but BEFORE the legacy management gate. The original legacy handler remains blocked by the fail-closed guard in protected modes; outside secure mode it retains historical behavior until separately retired. The new response retains legacy fields `ok`, `report`, and `summary`, plus transparent `mode: LOCAL_HTTP_HEAD_ONLY`, `browserAudited: false`, `healingPerformed: false`, `routeModified: false`. It does **not** report browser/JS/audit-and-heal PASS.
- Tests: strict URL/route oracle, userinfo and metadata-URL SSRF attempts, malformed/traversal/encoded paths, private debug/admin endpoints, blank/large JSON bodies, real ephemeral HTTP HEAD/redirect/500/404/timeout tests, deterministic network exception behavior, auth and source-order contract.

## Trust and explicit limitations

This is a **bounded partial restoration of /ai/audit HTTP reachability**, NOT a full site auditor. It cannot detect browser console errors, client JavaScript failures, mixed content inside assets, network waterfalls, app-level authentication defects, or safely perform a mutation. `POST /ai/ask`, `POST /ai/audit-and-heal`, and legacy advanced heal remain blocked. We do not silently mark `AI_HEAL_SCOPE_DEGRADED` green or exercise owner release authority based on this module. We cannot know whether all configured owner Origins map to the same requested route without post-cutover browser UAT. Only trusted admin users may trigger probe; no token/cookie forwarding. This work is independent of the concurrently authorized v85 current-image private recovery lane, touches none of that worker/archive code, and must be reconciled against the next actually returned Engineer-I SHA rather than overwriting its branch.
