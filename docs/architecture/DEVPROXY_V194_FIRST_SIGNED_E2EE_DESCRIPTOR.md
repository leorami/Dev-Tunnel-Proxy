## The security chain actually proven

`TEST-TRAJECTORY` (separate OS process) creates an ephemeral per-process Signal identity and an **independent** Ed25519 metadata-signing identity. The synthetic test coordinator observes the public keys only and pins a Signal peer public identity for each process. It injects the sender's **public signing key** into the simulated Calliope endpoint via a test-only configuration RPC; a real enrollment service is NOT implemented. It separately configures a fixed synthetic manifest and optional fixed trusted grant from hard-coded test values **inside Calliope**, never from a signed/encrypted sender request.

The trajectory test peer creates a V191 canonical `artifact.describe` record (sender, project, audience, SHA-256 digest, timestamp, expiry, nonce) and signs it with Ed25519. It encrypts that full signed metadata through official `@signalapp/libsignal-client@0.106.0` using the actual recipient's pinned Signal identity and PQXDH PreKey. The coordinator relays **only ciphertext and public enrollment information**; the private Signal ratchet key, Ed25519 signing private key and signed/decrypted plaintext stay inside the endpoint processes. The Calliope peer decrypts with official libsignal, parses bounded JSON internally, passes it to the **real V193** `createCalliopeArtifactDescriptorGate`, whose **real V191** verifier checks signature/domain/expiry/nonce and whose manifest/grant gate checks sender/project/digest/source/expiry. It returns a bounded inert metadata result with `ownerApprovalGranted:false`, `exportAuthorized:false`, `executionAuthorized:false`, `healingPerformed:false`, `liveAttested:false`, `productionChangeAuthorized:false`.

Negative integration checks cover missing separate trusted grant (even with valid encryption and signature), forbidden encrypted `artifact.export`, forged `ownerApproved`, modified signature, mismatched digest, and two different Signal ciphertexts containing the same signed nonce. Existing V192 wrong-identity/recipient/tamper/replay tests and V191/V193 signed/grant tests remain in scope. In a test-only worker, no real recipient/source identity, file content, filesystem locator or true owner permission is ever provided.

## Important limitations and future real design

1. **Two identities are not automatically one principal.** The test's Signal identity and Ed25519 signing identity are *separate* cryptographic keys, and synthetic trusted coordinator enrollment binds them by fiat. A live solution MUST atomically bind (device, Signal key, signed metadata key, project principal, owner-paired identity, grant scope), handle rotation, revocation and multi-device changes, and prevent one registered key silently being swapped under a different E2EE session.
2. **No durable messaging.** Signal session/ratchet state, V191 nonce replay state and synthetic grants exist only in memory. Restart, crash, concurrent workers, delivery reordering and device migration are **unsolved**. A real endpoint needs durable ratchet state with crash-safe single-writer transitions, durable atomic replay/idempotency, bounded ciphertext spool/retry and key revocation. Do not expose public or private service endpoints until designed/tested.
3. **Synthetic grant is NOT actual owner consent.** V193 accepts an object supplied by its constructing caller. The user may not be told `ownerApproved` because the fixture arbitrarily sets `withGrant:true`. A real service must source a trustworthy, owner-authenticated, immutable and revocable capability grant, enforce project/task/purpose/recipient/source/digest, and record a redacted audit; encryption/authentication does not substitute this.
4. **No file disclosure.** A digest, content type, length and source SHA describe a synthetic proposed artifact, not an existing safe owner file. No original PNG/bytes, paths, screenshots, GitHub evidence attachments or recipient-only file encryption are provided. CTO UI/UAT original-byte requirement remains separate and unfulfilled for historical V189 owner-private screenshot transport.
5. **AGPL/commercial release gate.** The official `libsignal` README says third-party use is **unsupported**, and `node/package.json@v0.106.0` declares **AGPL-3.0-only**. A source test using npm in a disposable CI runner is not approval to package the library into commercial apps or a server. Consult qualified counsel for distribution/network service obligations and obtain a practical maintenance/support decision; no claims of endorsement, commercial license or compliance are made.
6. **Node runtime.** `@signalapp/types@0.3.0` transitively requires Node >=24.18.1, while Dev Proxy owner API historically runs Node22. CI uses Node24 **only** inside disposable tests, not the owner app. A real deployment should choose a supported isolated runtime or an authorized platform upgrade, not silently replace the canonical owner app.
7. **Origin guidance optional.** Origin PR #154 remains draft, and automatic fleet policy adoption is not authorized. The inter-app transport must not infer task execution, merge, deployment or owner authority from a message.
8. **Real Trajectory contract.** Trajectory Room messages remain `executable:false` with exact task Mode intersect Dispatch. A *real* Trajectory integration must read its current accepted source and owner runtime, not old default `main`; no cross-repo modifications occurred here.
