## Independently source-verified problem
The V101 repository also contained an **older, separately executable** `utils/rc2-mac-host-worker.cjs` with its own `main()`. It directly loaded an operator pin through a weaker `loadPrivatePin()` (checking only a few file stat fields, unlike `loadVerifiedHostWorkerPin()`) and supported command-line `process-one` and `scan-once`. The CLI called `worker.processOne(id)` / `worker.scanOnce()` **without acquiring** the exclusive singleton. Thus an accidental legacy invocation could compete with the established supervised worker and bypass its collision/quarantine workflow. This is a *source-evidenced alternate entrypoint*, **not evidence** that an unauthorized live action actually occurred. Any local actor with full owner-UID privileges can modify local code; no JS-level mitigation is a sandbox against a malicious same-UID attacker.

## Small CTO source change
- `utils/rc2-mac-host-worker.cjs` now **only** exposes `createMacHostSettlementWorkerFromPin()` for the existing trusted supervisor. The historical weak `loadPrivatePin` export and implementation were retired. Legacy `main()` unconditionally rejects with a fixed `HOST_WORKER_SUPERVISOR_REQUIRED`, even when passed a pin and valid-looking nonce; standalone CLI exits 2, no secret/path strings printed, no pin read or spool write. The genuine V101 supervised entrypoint remains unmodified and retains `loadVerifiedHostWorkerPin()` + exclusive singleton acquisition.
- `tests/security/rc2-supervisor-only-direct-cli-guard.test.cjs`: six RED-first tests for unconditional denial of direct process-one/scan-once, sanitized stderr, absence of alternate weak pin loader, removal of the direct environment-pin shortcut, and preservation of the real supervisor's constructor.
