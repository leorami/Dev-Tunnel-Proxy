## Production-reported reproducible fault
The Owner-A RC2 cutover receipt `docs/receipts/DEVPROXY_RC2_OWNER_A_CUTOVER_ENGINEER_COMPLETION.md` explicitly records that on first startup nginx could not resolve the `dev-proxy-config-api` upstream until the API joined the Docker network. Engineer had to restart the proxy after API startup. The release receipt also reports the proxy's `RestartPolicy=no` and a cold Docker Desktop reboot-order hazard. Source review traced the problem to `utils/rc2-production-compose-candidate.cjs`: `proxy-config-api.depends_on=['proxy']`, the **reverse** of the actual nginx startup dependency, and neither service had a restart policy. Replaying the deployed source as-is has a reproducible bad launch order even if the live running pair is currently healthy.

## Important distinction: startup order vs reboot
Compose `depends_on` orders services during a Compose-managed `up`, but it does not necessarily order independent daemon restarts after a full Docker Desktop reboot. `restart: unless-stopped` lets an initially failed proxy retry once API DNS is ready; the real recovery behavior still requires isolated Mac Docker Desktop restart/reboot simulation and nginx/route re-attestation. This source change must **not** be casually imported into the active V101 host-worker scope: a change to service creation/restart behavior deserves its own disposable proof and separate implementation decision after V101 RETURNED.
