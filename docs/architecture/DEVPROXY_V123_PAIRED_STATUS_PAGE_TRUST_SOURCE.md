## Concrete still-existing browser-side security boundary

At the accepted V122 source, `status/status.html` Git blob `3a9eb28d3489f73ebf335ef937f9efbec2b0a319` loads three externally executable JavaScript resources with no SRI:
- `https://unpkg.com/lucide@latest` — floating unversioned.
- `https://cdn.jsdelivr.net/npm/marked/marked.min.js` — floating unversioned.
- `https://cdn.jsdelivr.net/npm/dompurify@3.0.6/dist/purify.min.js` — exact version but no integrity.

The page allows an explicitly paired local bridge bearer in `sessionStorage` and uses `Authorization: Bearer` to reach localhost. Any script executing in the same origin as that tab can access tab storage. SRI and version pinning mitigate supply chain changes but do not themselves protect against DOM XSS or inherently malicious dependencies. No actual CDN compromise, token theft, malicious page execution, or live browser exploit has been established. The bridge is offline and will remain so under this source-only assignment.

Source review found two unsafe HTML-interpolation sites: the Notification Settings header interpolated raw `source` and `route` into `title.innerHTML` (around old line 1601); the grouped config header interpolated raw `source` into `configHeader.innerHTML` (around old line 2563). Whether an attacker can influence these values depends on their provenance, not established. Additional status-log modal `innerHTML` templates interpolate log paths received from a bridge response; these must be independently audited before the paired browser UI can be considered hardened. There are more `innerHTML` sites elsewhere; don't claim a complete DOM XSS audit from two targeted replacements.
