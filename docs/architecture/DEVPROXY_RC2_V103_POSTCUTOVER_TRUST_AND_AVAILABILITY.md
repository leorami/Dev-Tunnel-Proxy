## Findings directly verified against accepted V101 source and receipt

1. **Public HTTPS login compatibility is likely broken.** V101 live runtime receipt lists only `http://127.0.0.1:8080` and `http://localhost:8080` in `DEVPROXY_TRUSTED_ORIGINS`, while the existing ngrok container is running and previously authorized static HTTPS browser ingress must be preserved. `adminRequestOriginAllowed()` in `utils/admin-session-security.cjs` performs exact origin membership; `POST /admin/login` invokes that gate and replies 403 for any HTTPS origin missing from the list. **SOURCE-LEVEL PREDICTION**, not proof of a real public HTTPS browser failure; actual current static domain and browser context must be privately confirmed on Mac, without putting hostname/token/password in GitHub. Never fix by wildcards, Host-derived trust, open CORS or bypassing CSRF.
2. **Anonymous management-health response leaks metadata.** Nginx explicitly exposes GET `/devproxy/api/ai/health` without auth. V101 secure branch returned `openaiConfigured:Boolean(process.env.OPENAI_API_KEY)`, dynamic `currentActivity`, and capability/model fields. The legacy fallback also ran `docker logs dev-ngrok` from this public health path to discover the static domain, then returned it along with an AI model and activity. There is **no evidence secret bytes were publicly returned**. This is still unnecessary credential-presence/activity disclosure and avoidable public-triggered subprocess execution.
3. **Cold-start race was experienced, not hypothetical.** Owner-A release receipt documented nginx failing to resolve API upstream on first start, a manual proxy restart, and live `RestartPolicy=no`. V101 production Compose candidate source had reverse `proxy-config-api.depends_on=['proxy']` and no restart policies. Correct source direction is nginx proxy depending on the API; Compose service-order policy alone does not guarantee Docker-daemon reboot ordering.
