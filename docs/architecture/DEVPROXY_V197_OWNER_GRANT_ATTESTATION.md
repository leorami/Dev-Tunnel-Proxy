## Trust contract — what the pure Node18-compatible helper verifies

`utils/calliope-owner-describe-grant.cjs` exports `createCalliopeOwnerGrantVerifier` and canonical `ownerGrantSigningBytes` used by ephemeral RED-first test fixtures. It accepts only a **pre-pinned Ed25519 public issuer key**, a separately pinned Ed25519 sender key, and trusted-context values for the current owner session digest, source commit, selected artifact SHA-256, project, sender, recipient, and recipient Signal identity fingerprint. It requires **real V196 branded durable replay ledger** and synchronous `isRevoked` + `isEnrollmentActive` callbacks supplied by a future trusted host. There is no libsignal dependency, Keychain, local file read, transport, grant signature minting, enrollment or UI.

A separately signed grant must carry exactly:
- version 1 and fixed domain/audience `devproxy.calliope.owner-describe-grant.v1`;
- fixed issuing role `trajectory-owner-session` (currently a **synthetic test issuer**, not a real owner account);
- hashed current owner session, sender/recipient, actual sender signing public-key hash, recipient Signal identity public-key hash;
- the precise project, **`artifact.describe` only**, selected artifact SHA-256 and sourceCommit;
- the **same nonce** as the independent request, grant issue time and maximum **60-second** validity;
- Ed25519 signature under the previously pinned issuer public key, canonical ordered domain-separated signed bytes.

A valid grant is checked *independently* from a real V191-signed `artifact.describe` request; the V191 verifier checks actual signature, exact registered sender/project, audience, intent, expiry, canonical fields and **V196 persistent nonce admission**. The grant's issuance timestamp must follow the signed request, so consent cannot be presumed from a free-floating preauthorization. The signed request must match the owner-grant's nonce, selected artifact digest, project and sender, and encompass the grant's validity. No caller-provided `ownerApproved`, paths, URLs, `artifact.export` or unknown field may be introduced.

**Security consequence:** A Signal-encrypted packet, a V191 agent signature, or a self-signed grant *alone* is insufficient. To produce an inert candidate, the actual signature under a pinned independent issuer key, paired device fingerprint, current session digest, independent requested artifact, owner revocation/active-enrollment checks and durable signed-message replay **all** must match. Unknown/offline/throwing/async callback denies rather than permitting. A further RED-first test [Actions #45318366829](https://github.com/leorami/Dev-Tunnel-Proxy/actions/runs/45318366829) identified that constructor configuration could incorrectly use the **same Ed25519 key as both grant issuer and agent signer**; this would let an enrolled agent self-issue grants. The root fix requires cryptographically distinct issuer and agent public keys, failing construction with `ISSUER_SIGNER_KEY_SEPARATION`. Final verified CI evidence follows after tests. The issuer signature and device pairing are intentionally separate identities; the real system must link them in a trusted enrollment ceremony.

Successful output is deliberately `SIGNED_OWNER_GRANT_CANDIDATE_ONLY`, and the flags `ownerApprovalGranted`, `exportAuthorized`, `executionAuthorized`, `healingPerformed`, `liveAttested`, `productionChangeAuthorized` are **always false**. This is an attested *record candidate*, not evidence a human actually approved a grant. Output never exposes a session ID, recipient key fingerprint, file path, URL, content, grant ID or original media bytes.
